# PipuPath Adventure Experience Constitution v1.0

**Status:** LOCKED — NON-NEGOTIABLE PRODUCT EXPERIENCE AUTHORITY  
**Effective:** 2026-08-20  
**Product:** PipuPath  
**Company:** KAEC-NG  
**Scope:** Every current and future Builder-facing experience

## 1. Constitutional law

PipuPath is a **Human Potential Adventure System**.

It is not a conventional education dashboard, productivity tracker, social network, LMS, career portal or SaaS application with game decoration added afterward.

> **The screen is not the game. Life is the game.**

The application exists to make real human development feel like an unfolding adventure: discover who you may be, choose a direction, face meaningful challenges, act in the real world, return with proof, learn from what happened, strengthen capability, build useful things and unlock larger opportunities.

This is architecture, not theme. It governs information hierarchy, navigation, state transitions, copy density, interaction patterns, animation, progression, choice, rewards, recovery and future feature design.

If a technically correct implementation does not make the developmental journey feel alive, it is incomplete.

## 2. Authority and precedence

This constitution is mandatory for agents, designers and engineers working in PipuPath.

When product implementation conflicts with this constitution:

1. privacy, safeguarding, security and truthful evidence rules remain absolute;
2. this Adventure Experience Constitution governs Builder-facing experience architecture;
3. the underlying released domain model and persistence contracts remain authoritative unless an explicit migration changes them;
4. implementation convenience does not justify adventure drift;
5. only an explicit new user/product authority may replace this constitution.

Future chats must not depend on prior conversational memory to recover this rule. `AGENTS.md` requires this document during agent startup.

## 3. The canonical adventure

The durable developmental engine remains:

`Discovery → Human Potential Profile → Possible Paths → Mission → Journey → Quest → Evidence → Reflection → Capability → Project → Portfolio / Connect → Collaboration → Living Builder Profile → AI Builder Guide → Capability Verification → Institution / Opportunity → Builder Passport`

The experience layer interprets it as:

- **Discovery = The Call** — uncover early signals about yourself.
- **Human Potential Profile = Potential Map** — see evidence-backed possibilities, not a permanent label.
- **Possible Path = Direction to Explore** — a hypothesis the Builder may test and later change.
- **Mission = Campaign** — the meaningful objective currently being pursued.
- **Journey = Adventure Map** — the visible route through developmental milestones.
- **Quest = Real-World Challenge** — one bounded challenge that requires action beyond the screen.
- **Evidence = Proof** — credible evidence of an attempt, result or contribution.
- **Reflection = Learn & Power Up** — convert experience, including failure, into insight.
- **Capability = Skill Tree** — evidence-backed abilities that strengthen through demonstrated action.
- **Project = Major Build / Boss Build** — combine capabilities into something real and useful.
- **Portfolio = Builder Vault** — selected proof of what has actually been built.
- **Connect / Collaboration = Allies** — safe relationships that help Builders accomplish meaningful work.
- **Opportunity = Deployment Door / New World** — a real place to use demonstrated capability.
- **Passport = Builder Identity** — portable, selective, credible evidence of who the Builder is becoming.

These adventure labels are an experience language. Domain terminology may remain stable in code and persistence.

## 4. The primary experience grammar

Every primary Builder screen should communicate five things in this order where applicable:

`Context → Current State → Next Move → Real-World Action → Consequence / Reveal`

### Context
Where am I in my larger adventure?

### Current State
What am I working toward now, and what has already been proven?

### Next Move
What is the single most meaningful thing I can do next?

### Real-World Action
What must happen outside PipuPath rather than merely on the screen?

### Consequence / Reveal
What truthfully changes, unlocks, strengthens or becomes visible after I act?

Secondary explanation belongs behind progressive disclosure.

A primary Builder page that instead leads with a feature catalogue, equal-weight card grid, long report, generic table, settings-like form or large vertical wall of prose fails the intended architecture unless that pattern is intrinsically required by the task.

## 5. Adventure Shell

The authenticated product shell must consistently reinforce that the Builder is inside one living adventure.

It should make available, directly or contextually:

- Builder identity / level;
- current Path and Campaign;
- current Journey state;
- one dominant Next Move;
- truthful progress / XP;
- meaningful recent unlock or capability growth where available;
- stable navigation escape.

Navigation labels may remain `Home / Journey / Build / Vault / Connect / Me`, but navigation must not make the product feel like six unrelated applications.

## 6. Required primary surfaces

### Adventure Home
Returning to PipuPath should feel like returning to an adventure already in progress.

Priority:
1. current direction / Campaign;
2. dominant Next Move;
3. Adventure Map progress;
4. truthful consequence, XP, level or capability signal;
5. relevant Build, Ally or Opportunity context;
6. secondary surfaces.

Never restore an equal-weight dashboard grid as the primary Home architecture.

### Potential Map
Discovery results must feel like a map of signals and possibilities, not a psychological report.

- concise signals first;
- deeper rationale on demand;
- uncertainty and provenance visible;
- Path choices framed as hypotheses to test;
- a clear bridge into action.

### Path choice and Path pivot
A Path is a **direction to test**, not a prison or permanent identity.

The Builder must be able to change Path when their evidence, interests, circumstances or learning changes.

A Path pivot must:

1. explain the consequence before confirmation;
2. preserve all prior truthful history;
3. preserve earned XP and evidence-backed capabilities unless a separate rule explicitly states otherwise;
4. pause or archive the incompatible active Mission/Campaign and unfinished Quests rather than rewriting them;
5. preserve evidence, reflections, completed Quests, Projects and provenance under the old Path;
6. record a lineage/audit transition from old Path to new Path;
7. allow the Builder to choose or generate a new Mission appropriate to the new Path;
8. provide an obvious route back to review previous adventure history;
9. never imply that changing direction is failure.

The Builder owns the adventure. The current Path does not own the Builder.

### Journey = Adventure Map
Journey is not primarily a task list.

It must communicate spatial or staged progression with clearly different states:

- completed;
- current;
- available choice;
- locked;
- reveal-later;
- milestone;
- Major Build / Boss Build when applicable.

The semantic/accessibility representation may be linear, but the felt experience should be progression through a route.

### Quest = Challenge Focus
Quest is not an article or checklist page.

The governing interaction is:

`Understand → Act → Prove → Reflect → Reveal`

The current phase is dominant. Supporting explanation is secondary. Completion should produce truthful visible consequence.

### Proof and Reflection
Submitting Proof is bringing evidence back from real life.

Reflection is not bureaucratic post-processing. It is where the Builder converts an attempt into learning and the system determines what can truthfully strengthen or unlock.

Failure may still generate insight, resilience, experimentation evidence or a changed next move; it must not fabricate achievement.

### Capability = Skill Tree
Capabilities must feel like something being discovered and strengthened over time.

No capability node may exist as a decorative score without evidence/provenance.

### Project = Major Build / Boss Build
Projects should feel like consequential builds that combine skills and produce useful output.

Project management mechanics may exist underneath, but the primary experience should communicate challenge, milestones, proof and outcome rather than generic task administration.

### Builder Vault
The Vault is proof of action and creation, not a media feed.

Private evidence stays private by default. Publication remains deliberate and selective.

### Opportunities = Deployment Doors
Opportunities should feel like new places to deploy demonstrated capability. Eligibility must be truthful and explainable.

## 7. Progression law

Progress must be caused by meaningful developmental activity.

Valid progression sources include:

- completing a real-world Quest;
- submitting meaningful evidence;
- reflecting on an attempt;
- completing a Project milestone;
- creating a useful artefact;
- collaborating safely on meaningful work;
- demonstrating a capability;
- creating real value;
- deploying work into an opportunity.

Invalid progression sources include:

- opening the app;
- viewing a page;
- clicking arbitrary buttons;
- consuming content without application;
- maintaining a meaningless streak;
- fabricated social activity.

The Builder must be able to see what changed because they acted.

## 8. Choice and agency law

Human development is not linear. PipuPath must support bounded, safe choice.

Where domain prerequisites permit it, Builders may:

- choose between valid next Quests;
- pause and resume;
- revisit previous evidence;
- change Path;
- abandon an obsolete experiment while preserving learning;
- begin a new Mission after an explicit transition.

Do not force a Builder through obsolete work solely because software state made it active earlier.

Choice does not mean unstructured chaos. Safety, prerequisites, evidence integrity and lifecycle rules still apply.

## 9. Copy and density law

Primary youth-facing copy is short, active, specific and mature.

The default page should not require reading an essay before acting.

Use:
- progressive disclosure;
- short challenge brief;
- expandable rationale;
- contextual help;
- visual state;
- milestone language;
- clear consequences.

Avoid:
- repeated explanations;
- long vertical report layouts;
- administrative jargon;
- motivational filler;
- childish fantasy language that damages credibility for older Builders.

Adventure is created by meaningful progression and consequence, not by renaming every button with fantasy vocabulary.

## 10. Motion and reveal law

Motion communicates state change, not decoration.

Useful examples:
- a path opens;
- a node completes;
- XP moves after verified progress;
- a capability strengthens;
- the next Quest reveals;
- a Major Build becomes available;
- a Project enters the Vault;
- a meaningful milestone receives a restrained celebration.

Every state remains understandable with reduced motion.

## 11. Forbidden drift patterns

The following patterns are warning signs and must be justified or redesigned when they dominate a primary Builder flow:

- generic SaaS dashboard grids;
- pages composed mainly of equal-weight cards;
- vertical walls of text;
- feature directories presented as the product experience;
- task lists with no larger Journey context;
- forms with no challenge/progression framing;
- XP or badges disconnected from evidence;
- gamification that rewards screen time;
- dead-end completion screens;
- locking a Builder into a developmental Path with no safe pivot;
- replacing real-world action with content consumption;
- decorative fantasy language without meaningful mechanics.

Beautiful styling does not cure architectural drift.

## 12. Mandatory retrofit rule

The released application must now be judged against this constitution.

Before introducing another major product layer, agents must inspect the primary Builder surfaces and classify each as:

- **Compliant** — genuinely feels like the Human Potential Adventure;
- **Partial** — correct mechanics exist but the experience is still substantially dashboard/form/card driven;
- **Drifted** — the main experience contradicts this constitution.

Materially Partial or Drifted primary flows become correction work before feature expansion unless the user explicitly chooses otherwise.

Do not rebuild working domain logic merely to change presentation. Preserve the released engine and retrofit the adventure layer over it.

## 13. Acceptance gate for every Builder-facing change

Before completion, answer yes to every applicable question:

1. Can the Builder understand where they are within seconds?
2. Is one next meaningful action obvious?
3. Does the action require or support something meaningful in real life?
4. Is the consequence of action visible and truthful?
5. Does progression feel staged, spatial, unlock-based, reveal-based or otherwise consequential?
6. Is reading subordinate to doing?
7. Is the Builder given meaningful agency where appropriate?
8. Can a changed direction preserve previous growth rather than destroy it?
9. Does failure produce a useful next move?
10. Are rewards grounded in evidence?
11. Does the flow remain mobile-first and accessible?
12. Are privacy and safeguarding preserved?
13. Can the Builder recover or leave without browser-only navigation?
14. Would this still feel like PipuPath if all decorative gradients and icons were removed?
15. Does this make the Builder want to **do something in real life**, not merely stay in the app?

If an applicable answer is no, the change is not Adventure-complete.

## 14. Agent execution rule

Every new agent or chat working on PipuPath must:

1. read `AGENTS.md`;
2. read this constitution;
3. read the current project state and relevant stage authority;
4. inspect existing implementation before proposing replacement architecture;
5. preserve released domain/persistence/safety contracts;
6. identify experience drift explicitly;
7. correct drift before unrelated expansion when the mandatory retrofit rule applies;
8. include Adventure acceptance in the definition of done and validation plan.

An agent must never say that PipuPath's adventure direction is merely a future visual enhancement. It is the current product architecture.

## 15. Final doctrine

PipuPath should make a Builder feel:

> **I know where I am. I know what I am trying to become. I can see the road ahead. I have a challenge worth attempting. I can act in real life, bring back proof, learn from what happened, grow stronger, change direction when the evidence tells me to, build something useful and unlock a bigger world.**

That is PipuPath.
